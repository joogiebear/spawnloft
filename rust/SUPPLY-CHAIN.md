# Rust supply chain

Policy (agreed 2026-11-05, kept by the 2026-11-08 Rust + Tauri plan):

- `Cargo.lock` is committed and every CI build runs with `--locked`.
- `cargo deny check` runs on every push: crates.io only, no git sources, the licence allowlist
  in `deny.toml`, and RustSec advisories (a yanked or vulnerable crate fails the build).
- The toolchain is pinned in `rust-toolchain.toml`.
- A direct dependency is added only by a commit that also adds it to the table below, saying who
  maintains it and why a smaller option or std would not do.

## Direct dependencies

| Crate | Used by | Maintainer | Why |
| --- | --- | --- | --- |
| `serde_json` (feature `preserve_order`) | spawnloft-lib: state files, the control protocol, the registry, metrics, the webhook body | dtolnay and the serde-rs team | Every file and message the daemon shares with Node is JSON. A hand parser would be a second JSON implementation to keep right on escapes, numbers and UTF-8; serde_json is the most used crate for it. `preserve_order` keeps keys in the order Node writes them, so state.json reads the same under both daemons. Its tree adds indexmap, hashbrown, foldhash, itoa, zmij and memchr. |
| `regex` | spawnloft-lib: the ready and failure patterns, the crash diagnosis shapes, TPS and `list` parsing | the rust-lang team | The patterns are shared with the Node daemon as JavaScript regexes; porting them by hand into string matching would drift. `regex` is maintained by the Rust project, linear time (no catastrophic backtracking on server log lines), and pulls only its own regex-automata, regex-syntax and aho-corasick. |
| `windows-sys` (Windows only) | spawnloft-lib `platform/windows.rs`: Job Objects, the named pipe and its DACL, process times and memory | Microsoft | Raw bindings to the Win32 calls the daemon needs and nothing else (feature-gated per API set). Generated from Microsoft's metadata; the alternative is hand-written `extern` declarations, which is where layout bugs come from. |
| `tauri`, `tauri-build` | spawnloft-shell: the window, WebView2 / WKWebView / webkit2gtk | the Tauri Programme (Commons Conservancy) | The shell choice of PLAN-RUST-TAURI.md section 1. Pinned exactly (`=`) because the NSIS template is a fork of this bundler release's (Q25). Its tree is most of the lockfile (about 430 of 495 crates, many Linux GTK and D-Bus crates); none of it is linked into `spawnloft-core`, which stays the small console binary. Four of those Linux crates are flagged unmaintained by RustSec and ignored by name in deny.toml with the reason. |
| `tauri-plugin-updater` | spawnloft-shell: the Phase 0 update cycle (Q21) | the Tauri Programme | Downloads the installer named by the core's verified record, verifies its minisign signature and signed version again, runs the NSIS installer with its own flags. Kept after the spike (Q21); it never fetches a feed of its own (INSTALLER-UPDATER-DESIGN.md 5.5). |
| `tauri-plugin-single-instance` | spawnloft-shell: a second launch focuses the open window | the Tauri Programme | What Electron's `requestSingleInstanceLock` did in 1.x. Pulls zbus on Linux. |
| `serde_json` | spawnloft-shell | as above | `tauri::generate_context!` names it at the crate root. |
| `minisign-verify` | spawnloft-lib `update`: verifies the signed envelope and the downloaded installer against the pinned release keys | Frank Denis (jedisct1, minisign's author) | The same minisign format and author as the signing tool and as the verifier inside `tauri-plugin-updater`, so the core and the shell cannot disagree on what a valid signature is. Verify-only: no key generation, no signing, and no dependencies at all (Ed25519 and BLAKE2b are implemented inside, about 1500 lines). A hand-rolled Ed25519 or BLAKE2b of our own is exactly what the policy forbids. |
| `semver` | spawnloft-lib `update` (ordering, pre-release channels, `minVersion`) and spawnloft-core `update` | dtolnay | Version comparison with pre-release rules is where updaters go wrong (`2.0.0-beta.10` vs `2.0.0-beta.9`); this is the implementation Cargo itself uses, with no dependencies. |
| `sha2` | spawnloft-lib `update`: the envelope's `sha512` of each artifact, checked after the download | the RustCrypto team | Binds the downloaded bytes to the signed envelope, in addition to the minisign signature over them. Pure Rust, constant-time, audited; pulls `digest`, `crypto-common`, `generic-array`, `cpufeatures`. |
| `ureq` (features `rustls`, no defaults) | spawnloft-lib `update`: fetches the release listing, the envelope and (headless `update apply`) the installer | Martin Algesten | A blocking client fits a check that runs in a subprocess of the shell; `reqwest` would add tokio and hyper to the console binary. rustls with the bundled `webpki-roots` so the TLS trust does not depend on the host's store (the plugin inside the shell already uses the same stack through reqwest). Request and response sizes are capped by the caller. |
| `hmac` | spawnloft-lib `panel_auth`: signs and checks the panel's sign-in tokens (HMAC-SHA256 over the install's key) | the RustCrypto team | The MAC and its constant-time comparison are exactly what the policy says not to write by hand. 0.13 is the release built on the `digest` 0.11 that `sha2` 0.11 already brings; the older `hmac` in the lockfile arrives through the dev-only `minisign` and is on `digest` 0.10. Adds `cmov` and `ctutils` (RustCrypto's constant-time helpers), nothing else. |
| `getrandom` | spawnloft-lib `panel_auth`: the install's key, session ids and login nonces | the rust-random team | std has no source of random bytes; this is the thin wrapper over the operating system's (`getrandom(2)`, `BCryptGenRandom`, `getentropy`) that `rand` and rustls themselves sit on, and it was already in the lockfile. No user-space generator of our own. |
| `minisign` (dev-dependency only) | spawnloft-lib tests: throwaway keys and signatures for the refusal tests | Frank Denis (jedisct1) | The tests need to produce valid and tampered signatures in-process; this is the reference implementation of the format and never reaches a shipped binary. |
